# Phase 30 — защита от устаревших результатов моделей

## Что добавлено

- `ModelRunFreshnessService` читает указатель активной версии проекта, запуски моделей и сохранённые результаты в одной readonly-транзакции IndexedDB.
- Для каждого запуска определяется статус `fresh`, `stale`, `legacy` или `unverifiable` и возвращается объяснение для UI.
- Результаты группируются по `runId`, а список запусков сортируется от новых к старым.
- Добавлены индексы `projectId_datasetVersion` для `modelResults` и `scenarioResults`; версия схемы БД повышена до 6. При обновлении существующей БД индексы создаются штатным `onupgradeneeded`.
- Добавлены unit-тесты классификации свежести.

## Правило отображения

- `fresh`: версия запуска совпадает с `projects.activeDatasetVersion`.
- `stale`: версия запуска отличается от активной — нельзя показывать результат как актуальный.
- `legacy`: у запуска нет `datasetVersion`; его свежесть нельзя предполагать.
- `unverifiable`: активная версия не опубликована, сравнение невозможно.

## Ограничения / следующий шаг

Этот сервис пока является инфраструктурным контрактом для экранов моделей: существующие legacy-экраны и исполнители моделей ещё не переведены на обязательную запись `datasetVersion` и не используют этот guard повсеместно. Поэтому это не означает, что все результаты старого UI уже защищены. Следующий этап — внедрить сервис в каждую точку отображения моделей/сценариев и при создании запусков сохранять версию снимка, из которого считались результаты.

Тесты и production build в текущем окружении не подтверждены: в архиве нет `node_modules`; предыдущая проверка блокировалась отсутствующими `vitest` и типами `vite/client`.
